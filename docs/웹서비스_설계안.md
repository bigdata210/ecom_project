# 측정대행업 문서 변환 웹서비스 설계안

작성일: 2026-10-28

## 1. 사업 범위와 전제

- 한 업체에서 먼저 시범 운영하고, 검증 후 여러 업체로 확대한다.
- 기존 유기인·VOC·중금속 PDF 추출 및 XLSX 작성 코드는 웹 처리 엔진의 출발점으로 재사용한다.
- 사용자는 홈페이지 로그인 후 측정 원본 PDF/Excel을 업로드하고 출력 양식을 선택한다.
- LLM은 문서 종류·표 구조·항목 연결의 후보를 만들고, 검증 코드와 담당자 확인을 거쳐 결과를 확정한다.
- 초기에는 등록된 출력 양식을 지원한다. 임의의 Excel 양식을 무검토로 완벽하게 변환하는 기능은 범위에 넣지 않는다.
- 외부 LLM으로 전송할 수 있는 정보의 범위와 검토 후 확정 여부는 사용자 답변에 따라 확정한다. 이 문서는 검토 후 확정을 기본 제안으로 한다.

## 2. 권장 기술 구성

| 부분 | 제안 | 역할 |
|---|---|---|
| 코드 관리 | 비공개 GitHub 저장소 | 웹·처리 코드, DB 변경 이력, 검증용 비식별 자료 관리 |
| 홈페이지 | Next.js + Vercel | 로그인 화면, 업로드, 검토, 다운로드, 이력 조회 |
| 로그인/DB/파일 저장 | Supabase Auth + PostgreSQL + Private Storage | 사용자·업체·작업·측정 데이터·원본·결과 관리 |
| 대기열 | Cloud Tasks | 처리 요청의 지연·재시도·동시 실행량 제어 |
| 처리 서버 | Python 컨테이너 + Cloud Run | PDF/Excel 분석, OCR 연결, LLM 호출, 검증, XLSX 작성 |
| LLM | 공급자 교체 가능한 API 연결 계층 | 구조 해석, 새 양식의 항목 매핑, 후속 요약 |

단일 업체 시범 운영에서는 웹·워커를 각각 하나의 서비스로 배포하고 DB도 하나를 사용한다. 처음부터 업체별 식별자를 저장하되 복잡한 서비스 분할과 벡터 DB는 도입하지 않는다.

Vercel의 Python Functions 또는 Workflow로 처리하는 대안도 가능하다. 다만 기존 Python 코드 재사용, OCR/문서 처리 라이브러리, 긴 처리 및 재시도를 고려해 별도 Python 워커를 기본안으로 제안한다. 이는 Vercel에서 처리할 수 없어서가 아니라 책임과 실행 환경을 나누기 위한 선택이다.

## 3. 사용자 흐름

1. 초대받은 사용자가 로그인한다. 관리자는 직원과 검토자를 초대한다.
2. 고객사·사업장·접수번호·분석 배치를 선택하거나 새로 만든다.
3. 파일을 업로드한다. 파일의 용도를 측정 원본 / 빈 출력 양식 / 완성 예시로 구분한다.
4. 시스템이 종류를 판별한다. 지원되는 문서의 기존 추출기를 먼저 사용한다.
5. 새 형식이면 LLM이 필드와 원본 위치를 제안한다. 불명확한 값은 확인 필요로 남긴다.
6. 등록 양식에 맞춘 결과 초안을 만들고 검토 화면에 표시한다.
7. 담당자가 원본 PDF 페이지 또는 Excel 셀과 추출값·계산값을 비교하고 수정한다.
8. 검토자가 확정하면 확정 데이터와 결과 파일 버전을 저장한다.
9. 권한이 있는 직원이 결과를 다운로드하거나 이력을 조회한다.

초안도 DB에 저장하지만 상태를 구분한다. 확정 전 데이터는 과거 대비 분석의 확정 결과로 사용하지 않는다. 검토 중 수정하면 초안을 다시 생성하고, 이미 확정된 결과를 바꾸는 경우 새 개정판을 만든다.

## 4. 업로드와 비동기 처리

브라우저 → 인증된 API에서 업로드 권한 발급 → 비공개 Storage 직접 업로드 → 업로드 완료 확인 → DB에 작업 생성 → 대기열 → 워커 처리 순서로 구성한다.

- 대용량 PDF를 Vercel API 요청 본문에 담지 않는다. 권한 검사를 거쳐 Storage에 직접 업로드한다.
- 대기열에는 파일 자체나 공개 URL 대신 작업 ID를 넣는다.
- 워커는 작업 ID의 업체·파일·양식 버전을 DB에서 확인하고 파일을 가져온다.
- 작업 생성과 대기열 발행 사이의 장애에 대비해 발행 재시도 기록을 두고 누락 작업을 복구한다.
- 동일 작업이 재전달되어도 단계별 처리 키로 중복 실행·중복 확정을 막는다.
- 업로드 완료 전에 작업을 실행하지 않는다. 완료 후 실제 파일 크기·형식·해시를 확인한다.
- 브라우저가 닫혀도 작업을 계속하고 다시 접속하면 상태를 조회한다.
- 초기는 상태 조회 요청 방식으로 진행률을 표시하고 필요할 때 실시간 갱신을 추가한다.
- 실패 원인·재시도 횟수·비용을 기록하고, 상한 이후에는 담당자가 재시도하도록 한다.

작업 상태 제안: 업로드 대기 → 대기열 → 추출 중 → 검증 중 → 검토 대기 → 확정 → 다운로드 가능. 실패·취소 상태는 별도로 둔다. 확정 후 내보내기가 실패하면 확정 데이터는 보존하고 내보내기만 재시도한다.

## 5. LLM과 계산 엔진의 역할

### LLM이 제안할 것

- 유기인·VOC·중금속 등 문서 종류와 기기 보고서 형식.
- 시료명·항목명·단위·표 머리글·측정값 후보와 원본 위치.
- Excel의 시트·병합·표 영역·머리글·수식 요약을 바탕으로 입력할 셀과 반복 행 구조.
- 새 양식의 매핑 초안 및 확인이 필요한 모호한 부분.

### 코드가 검증·실행할 것

- 자료형, 숫자 부호, 소수 자릿수, 단위, 중복 시료, 누락 필드 검사.
- 원본에서 숫자가 확인되는지 대조. JSON 형식 준수가 정확성 보증은 아니다.
- 검량표준·Blank·QC·실제 시료를 구분해 저장.
- 승인된 규칙에 따른 단위 변환·Blank 차감·희석배수·반올림.
- 승인된 셀 매핑에 따라 XLSX 작성, 필수 시트·수식·차트·출력 파일 수 검사.

LLM이 실행할 Python 코드나 Excel 수식을 자유롭게 만들어 실행하게 하지 않는다. 허용된 매핑과 계산 규칙만 실행한다. 문서 내부에 모델에게 지시하는 내용이 있어도 데이터로 취급한다.

측정값은 원문 문자열, 정규화한 십진수, 원단위·표준단위, 변환식, 원본 페이지/셀을 함께 저장한다. 빈칸·0·불검출·정량한계 미만·음수·`>999.9%` 같은 상한값은 서로 다른 상태로 관리한다.

시료 연결은 업체·접수/배치·시료 ID로 확인한다. 여러 PDF에 W-1이 있다고 같은 시료로 자동 병합하지 않는다. PDF와 기기 Excel의 값이 충돌하면 충돌을 표시하고 출처 우선순위를 확인한다.

## 6. 출력 양식 운영

1. 업체 관리자가 빈 양식과 완성 예시를 등록한다.
2. LLM이 항목 → 시트 → 셀/반복 행 매핑을 제안한다.
3. 담당자가 셀 위치·수식 보존·반복 행·시료 연결 규칙을 확인한다.
4. 기준 데이터로 자동 입력 결과와 수작업 정답을 비교한다.
5. 승인된 양식 버전을 이후 작업에서 재사용한다.
6. 양식의 시트·머리글·수식 구조가 달라지면 새 버전으로 재검토한다.

업체별 양식, 양식 버전, 계산 규칙 버전을 따로 관리한다. 단일 셀의 변경뿐 아니라 인쇄영역·차트·수식 범위의 변화도 검증한다. 기존 코드의 고정 시료 행 제한은 반복 영역 매핑으로 확장한다. 늘릴 수 없는 양식이면 추가 파일로 나누는 방식을 등록한다.

기존 출력 동작은 유지한다: 유기인+VOC는 묶음 구성에 따라 통합 XLSX, 중금속은 1차·2차 XLSX. 중금속 작업은 두 결과가 모두 생성된 뒤 한 쌍으로 게시한다.

초기 양식은 XLSX를 기본으로 하고 XLS는 등록 시 변환한다. Windows Excel COM에 의존하지 않도록 한다. 수식 캐시와 표시 결과도 검증한다. 매크로·복잡한 차트·외부 링크는 보존 가능 범위를 따로 확인하며, 검증되지 않은 기능의 완전 보존을 약속하지 않는다.

## 7. DB와 파일 저장 구분

| 데이터 묶음 | 핵심 내용 |
|---|---|
| organizations / memberships | 업체, 직원, 관리자·작업자·검토자 권한 |
| projects / batches / samples | 고객사·사업장·접수번호·분석 배치·시료 ID |
| source_files | 파일 용도, Storage 경로, 해시, 크기, 업로더, 보관 상태 |
| templates / template_versions | 양식 원본, 승인된 매핑, 변경 이력 |
| processing_jobs / job_steps | 입력 묶음, 처리 단계, 실패·재시도, 규칙·모델 버전, 사용량 |
| extraction_runs / measurements | 원본값, 정규화값, 출처 위치, 검증 상태, 사용자 수정본 |
| review_events / result_versions | 수정 전후, 수정 사유, 검토자, 확정 시각, 확정 개정판 |
| output_artifacts / audit_logs | 결과 파일 경로, 생성 기준 버전, 다운로드·삭제·관리 작업 이력 |

파일은 비공개 Storage에, 검색·비교할 구조화 데이터와 파일 메타데이터는 PostgreSQL에 둔다. 파일 바이트를 일반 측정 테이블에 직접 넣지 않는다. 시범 운영에서 벡터 DB는 필수 요소가 아니다.

업무 테이블과 파일 메타데이터에는 organization_id를 둔다. 사용자 요청이 보낸 업체 ID를 신뢰하지 않고 로그인 계정의 소속을 검사한다. 자식 데이터의 부모 연결도 같은 업체에 속하는지 DB 제약과 서비스 코드로 확인한다.

원본은 변경하지 않고 수정본·확정본을 별도 버전으로 만든다. 모델 이름·프롬프트 버전·입력 해시·양식 버전·규칙 버전·코드 버전과 실제 LLM 응답을 보관해 결과의 생성 근거를 추적한다. 같은 모델을 다시 호출해도 동일 결과가 나온다고 가정하지 않는다.

## 8. 권한과 운영

- 초기는 공개 회원가입보다 관리자 초대를 사용한다.
- DB RLS와 Storage 접근 정책에 업체별 제한을 건다. 화면에서만 목록을 숨기는 방식에 의존하지 않는다.
- 관리자 우회 키는 서버에만 둔다. 우회 권한을 가진 워커에도 업체와 작업 소유권 검사를 적용한다.
- 다운로드 요청마다 권한을 확인하고 짧은 유효기간의 주소를 발급한다. 공유된 주소는 만료까지 접근 가능하므로 노출 범위를 줄인다.
- 파일의 확장자·실제 형식·크기·페이지 수·압축 해제량을 검사하고 실행 가능한 매크로 및 임의 외부 참조를 실행하지 않는다.
- LLM 전송 전에 허용된 정보만 추출한다. 필요한 경우 시료·업체 식별자를 치환하고 복원 정보는 별도로 보관한다.
- 전송 허용 여부뿐 아니라 공급자의 보관·학습 사용 조건, 처리 지역, 업체 계약 요건을 확인한다. 국내 리전을 선택하는 것만으로 외부 LLM 처리가 국내로 제한되지는 않는다.
- 원본과 결과의 보관기간, 삭제 권한, 백업 복원 절차를 정한다. DB 백업과 파일 백업은 별도로 확인한다.
- 운영/개발 환경을 분리하고 운영 원본을 미리보기 배포나 공개 로그에 사용하지 않는다.

## 9. Git과 배포

비공개 저장소에 코드를 관리한다. Git에 올릴 것은 소스·DB 마이그레이션·프롬프트/규칙 스키마·비식별 테스트 자료다. 실측 PDF·고객 Excel·생성 결과·키·로그·EXE 빌드 산출물은 제외한다. 업체 양식도 고객 정보가 있으면 Storage에 두고, 저장소에는 비식별 기준 양식만 둔다.

제안 구조:

```text
apps/web/                 로그인, 업로드, 검토, 다운로드
services/processor/      Python 추출·LLM 연결·검증·내보내기
packages/schemas/        작업·필드·매핑 데이터 구조
supabase/migrations/     테이블·권한 변경 이력
tests/fixtures/          비식별 정답 세트
docs/                    설계·운영·양식 등록 가이드
```

PR 생성 → 자동 테스트 → Vercel 미리보기 확인 → main 반영 → 웹 배포 순서로 운영한다. Python 워커 배포와 DB 마이그레이션도 별도 파이프라인으로 관리한다. 이전 작업은 작업 생성 시점의 양식·규칙 버전을 유지한다. 미리보기 환경은 테스트 DB/Storage를 사용한다.

## 10. 개발 순서와 완료 기준

| 단계 | 구현 | 완료 기준 |
|---|---|---|
| 0. 업무 정의 | 파일 역할, 시료 식별, 계산·검토 규칙, 보관·외부전송 정책 | 실제 기준 예제와 수작업 정답 확보 |
| 1. 웹으로 기존 기능 이전 | 초대 로그인, 업체, 업로드, 작업 대기열, 기존 세 종류 변환, DB/Storage, 다운로드 | 기존 정답 세트와 일치하고 중금속 두 파일 게시 성공 |
| 2. LLM 보조 | 새 형식 판별, 항목/셀 매핑 제안, 원본 대조 검토, 수정·확정 이력 | 새 양식 등록을 승인 후 재사용하고 누락 숫자를 만들어 넣지 않음 |
| 3. 업체 내 시범 운영 | 실제 담당자 사용, 오류·수정 빈도·처리시간·비용 측정 | 예외 목록 해소 및 담당자의 실무 수용 확인 |
| 4. 다업체 확장 | 업체 가입·초대 정책, 접근 제어 검증, 사용량·운영 관리 | 다른 업체의 조회·다운로드·수정이 모두 차단됨 |
| 5. 전후 비교 | 확정 데이터에 근거한 2~3줄 요약 | 같은 지점·시료 조건·항목·단위·기간의 비교 가능성 확인 |

핵심 검증 항목은 문서 분류, 원본 대비 숫자 일치, 단위와 부호, 올바른 시료/셀 대응, 빈값과 불검출 구분, 수식·표시 검증, 중복 처리·중단 후 복구, 업체 간 접근 차단이다. LLM의 자기 평가 점수만으로 자동 확정하지 않는다.

개발 기간은 자료 다양성과 계산 규칙 확정 후 산정한다. 무제한 양식·OCR·자동 확정·법정 기준 판정까지 첫 버전에 함께 넣지 않는다.

## 11. 비용 관리

기존 하루 50건을 작업일 22일로 가정하면 월 1,100건이다. 이는 용량 산정용 가정이며 페이지 수와 파일 크기는 미확정이다.

월 비용 = 웹/DB 기본 비용 + 원본·결과·백업 저장 비용 + 워커 실행 비용 + OCR 페이지 비용 + LLM 입력/출력 사용량 + 다운로드 트래픽 + 재처리 비용.

먼저 실제 자료로 건당 페이지 수·토큰 사용량·처리시간·수정률을 측정한다. 이미 승인된 형식은 규칙 추출을 재사용하고 새 형식·모호한 부분에 LLM을 집중해 비용과 결과 변동을 줄인다. 업체별 월 한도와 작업별 재시도 상한을 설정한다. 정확한 금액은 공급자와 사용량을 확정한 뒤 산정한다.

## 12. 추가 확인 사항

1. 외부 LLM에 원본을 전송할 수 있는지, 식별자 제거가 필요한지.
2. 업체별 고정 양식 등록인지 매번 임의 양식 업로드인지.
3. 담당자 검토 후 확정인지, 일부 업무만 자동 확정할 것인지.
4. 측정 원본 Excel도 입력할지, PDF만 입력하고 Excel은 양식으로 사용할지.
5. 한 업체의 사용 인원·동시 사용자·하루 처리량·평균 페이지 수.
6. 기존 예시 외에 시료 실측값이 있는 문서와 계산 규칙을 확보할 수 있는지.
7. 초기 월 운영 예산, 데이터 보관기간, 처리 지역 요건.
